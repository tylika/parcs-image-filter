# Паралельна фільтрація зображень у PARCS (Google Cloud)

Лабораторна робота №1 з дисципліни «Хмарні обчислення».
Тема: **Паралельна фільтрація зображень: Гауссове розмиття та виявлення контурів оператором Собеля**.

Зображення в градаціях сірого спочатку розмивається Гауссовим ядром 5×5, потім для нього
рахується модуль градієнта Собеля. Паралельна версія ділить зображення на *k* горизонтальних
смуг із перекриттям у 3 рядки. Воркери PARCS фільтрують свої смуги (map), а майстер
відкидає перекриття і склеює результат (reduce). Результат паралельної версії побайтово
збігається з послідовною (це перевіряється за md5 у кожному запуску).

Кластер: Google Cloud Platform, Compute Engine, 1 майстер + 4 воркери, n1-standard-1,
Container-Optimized OS; контейнер `hummer12007/parcs-node` (parcs-python: Python 2.7 + Pyro4)
запускається стартовим скриптом ВМ (`docker run --network host`).
Проєкт GCP спільний з одногрупником: усі мої ресурси мають префікс `yulparcs-`, скрипти працюють лише з ними.

## Структура

```
solution/solution.py        розв'язок для PARCS: послідовний і паралельний алгоритм (один файл)
bench/run_benchmark.py      драйвер замірів через REST API PARCS (надсилає задачі, збирає час)
tools/run_local.py          перевірка коректності й запуск без хмари
tools/photo_to_pgm.py       фото -> PGM у відтінках сірого (потрібен Pillow)
tools/make_test_images.py   синтетичні тестові зображення 1024/2048/4096
tools/pgm_to_png.py         PGM -> PNG для звіту
scripts/config.ps1              Project ID, префікс yulparcs, зона, тип ВМ
scripts/01-create-cluster.ps1   створити кластер у GCP
scripts/02-run-benchmark.ps1    заміри на вже створеному кластері
scripts/03-delete-cluster.ps1   видалити МІЙ кластер (лише yulparcs-*) і перевірити, що нічого не лишилось
scripts/04-diagnose.ps1         діагностика, якщо щось не запускається
scripts/00-local-docker-test.ps1  (необов'язково) репетиція в Docker Desktop
docker/docker-compose.yml   локальний PARCS (майстер + 4 воркери)
docs/CHEATSHEET.md          шпаргалка для захисту
```

## Що треба встановити

| Що | Навіщо | Як |
|---|---|---|
| Google Cloud SDK (gcloud) | керувати хмарою зі скриптів | `winget install --id Google.CloudSDK -e`, потім **відкрити нове вікно** PowerShell |
| Python 3 | драйвер замірів, локальні перевірки | уже є |
| Pillow (необов'язково) | конвертувати своє фото і зберегти PNG | `py -m pip install pillow` |
| Docker Desktop (необов'язково) | репетиція без хмари | уже є |

Сторонніх Python-бібліотек для замірів не потрібно. У Docker-образі PARCS немає ні Pillow, ні numpy
(лише Pyro4, Flask, requests), тому алгоритм працює з «чистими» масивами пікселів.

## Покроково

Усі команди виконуються в PowerShell **у папці проєкту**
(у Провіднику: відкрити папку, у рядку адреси написати `powershell` і натиснути Enter).

**1. Вхід у gcloud:**
```powershell
gcloud init
```
Увійдіть buriak.yuliana@knu.ua і виберіть проєкт `project-a53af79b-1c08-4c03-95e`
(якщо його немає у списку, введіть вручну). Project ID уже записаний у `scripts\config.ps1`.

**2. Переконайтеся, що кластер одногрупника видалено.** Ліміт проєкту 8 vCPU, а кластер займає 5,
тож одночасно може працювати лише один. Скрипт створення сам перевіряє квоту і зупиниться, якщо місця немає.

**3. (Необов'язково, 10 секунд) перевірка алгоритму на своєму комп'ютері:**
```powershell
py tools\run_local.py check
```
Очікується `RESULT: all checks passed`.

**4. Створити кластер** (5–10 хв, скрипт сам дочекається запуску PARCS):
```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\01-create-cluster.ps1
```
Наприкінці з'явиться адреса `http://<IP>:8080`. Її можна відкрити в браузері: це веб-інтерфейс
PARCS, на сторінці *Workers* видно 4 воркери. Зробіть скриншот для звіту.

**5. Заміри** (≈10–20 хв):
```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\02-run-benchmark.ps1
```
Щоб у звіті було ще й ваше фото (потрібен Pillow):
```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\02-run-benchmark.ps1 -Photo C:\шлях\до\фото.jpg
```
Якщо заміри обірвались, продовжити з місця зупинки можна так: `... 02-run-benchmark.ps1 -Resume`.
Результати лежать у `results\gcp\`, а архів для звіту в `results\gcp-results.zip`.

**6. ОБОВ'ЯЗКОВО видалити кластер:**
```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\03-delete-cluster.ps1
```
Скрипт покаже список (лише `yulparcs-*`), попросить підтвердження, видалить ВМ, диски й правила
брандмауера і перевірить, що нічого не лишилось. Чекайте зеленого напису **«OK: КЛАСТЕР ВИДАЛЕНО»**,
а потім напишіть одногрупнику, що проєкт вільний.

**7. Надіслати** `results\gcp-results.zip` для генерації звіту.

**8. GitHub** (для розділу 10 звіту): на https://github.com → *New repository* → назва
`parcs-image-filter` → *Public* → *Create*. Потім *uploading an existing file*: перетягніть усі
файли й папки проєкту, крім `results` і `data`, і натисніть *Commit changes*.

## Якщо щось пішло не так

| Симптом | Що робити |
|---|---|
| `gcloud : The term 'gcloud' is not recognized` | gcloud не встановлено або вікно PowerShell старе: відкрийте нове |
| `...cannot be loaded because running scripts is disabled` | запускайте саме через `powershell -ExecutionPolicy Bypass -File ...` |
| «недостатньо вільних vCPU» | працює кластер одногрупника: дочекайтесь, поки він його видалить |
| «не вдалося створити майстра в жодній із зон» | змініть `$Region` / `$Zones` у `scripts\config.ps1` (наприклад, europe-west4 і europe-west4-a/b/c) |
| «підключилось воркерів: 2 з 4» | зачекайте 2–3 хв і відкрийте `http://<IP>:8080/workers`; якщо не допомогло, запустіть `04-diagnose.ps1` і надішліть вивід |
| будь-яка інша помилка | надішліть повний текст помилки |

## Що і як вимірюється

* 3 розміри синтетичного зображення: 1024², 2048², 4096² (детерміноване, однакове в усіх запусках).
* Конфігурації: послідовна версія (на майстрі) і 1, 2, 3, 4 воркери, по 3 запуски «по колу»: спершу перший запуск усіх конфігурацій, потім другий, потім третій
  (так повільні зміни продуктивності ВМ розподіляються між конфігураціями рівномірно).
* Перед замірами виконується «прогрівальна» задача, вона в статистику не йде.
* Час міряється всередині розв'язку (`time.time()`), без накладних витрат PARCS на запуск задачі:
  * `t_split`: майстер готує смуги з перекриттям;
  * `t_map`: розсилка смуг, фільтрація на воркерах, повернення результатів (паралельно);
  * `t_merge`: майстер відкидає перекриття і склеює;
  * `t_total = t_split + t_map + t_merge`;
  * `t_compute`: чистий час фільтрації на воркері (`t_compute_max` береться по найповільнішому);
  * `t_comm = t_total − t_compute_max`: передача даних, серіалізація, RPC, підготовка і склеювання.
* Прискорення S = T_посл / T_k, ефективність E = S / k.
* `summary.csv` містить середні значення, а `raw.csv` і `workers_detail.csv` усі запуски і кожен воркер окремо.
